# 评审教训（lessons）——三轮评审沉淀

> 来源：2026-09-14 三轮文档评审（初稿评审 5 条 → 第二轮 16 条 → 第三轮 11 条）。这些是"差点写进文档的错误"，比正确结论更值得复用。新文档/新评审前先过一遍。

## L1 · 账目必须平，"去重后变多"是逻辑错误

候选池曾写"~45 条去重后定稿 50 条"——去重只会减不会增。且初审对照 oxlint/ESLint 内置发现 ~15 条直接重合（no-fallthrough、no-self-compare、no-eval…），真正差异化的只剩 ~25 条。
**沉淀**：任何数量目标先做一遍"去重/重叠"的算术再写进文档；目标改成「自有差异化 25~30 条 + 内置启用映射清单」后 M1 性价比反而更高——通用规则不自建是特性不是妥协。

## L2 · 指纹锚点用稳定标识，不用可变文本

指纹初稿 = hash(ruleId+位置+**语义位置**)，但 oxlint JSON 是否携带语义上下文未验证；第二版含**消息模板文本**，改一条文案 = 全量历史指纹失效，平台复核流与抑制登记全断。
**沉淀**：跨系统的稳定标识只允许由稳定字段构成（ruleId + span + **messageId**）；语义锚点必须先有字段完备性实测（spike ④）才能入指纹；对外标识字段的增删/改名 = breaking，走显式评审。

## L3 · 消解模型要覆盖"跨名接管"，同名升级不够

消解层初稿只覆盖 ◆ 规则同名升级（JS 版 retired）。但 M1 自建的 `lintsight/no-floating-promise` 在 M2 由 `typescript/no-floating-promises`（--type-aware）**跨名**接管——按"不同 ruleId 不合并"规则，M2 上线即语义双报。
**沉淀**：设计消解/去重逻辑时，枚举所有"同一问题、不同标识"的来源：同名升级、跨名接管（type-aware/内置）、不同规则同 span（合法共存，输出 dedupGroup）。

## L4 · 接口冻结必须标注生效范围

rule-sdk "M1 冻结初版" 里包含 `onProgramEnd`，但 M1 的 JS 轨道（oxlint JS Plugins per-file 模型）根本没有这个钩子——冻结了一个兑现不了的接口。
**沉淀**：冻结接口时逐钩子标注生效里程碑（M1: create/onFileStart/visitor/onFileEnd；M2: onProgramEnd/createProgramRule）；"冻结的是接口形状与演进纪律，不是当前里程碑的全量兑现"。

## L5 · 自建 vs 复用的判断顺序：先算"重写什么"，再算"差异化值多少"

多次评审中反复出现的模式：方案看似在写核心价值（DFG/taint），实际大头是重写基础设施（调度/规则面/诊断）。判定公式：**直接自建的前提 = 重写成本 < 复用摩擦，且关键人手 ≥ 差异化模块的真实需求**。lintsight 的结论是 sidecar 双引擎；若前提变化（≥3 编译器工程师、无平台交付压力），结论可翻转——所以 spike ① 的实测数据是路线的最终裁判。

## L6 · 需求数量与粒度的分层纪律

- 需求清单先去重再定数量（→ L1）；
- 任务清单分层滚动：M0 执行级、M1 任务域（标 gate）、M2/M3 占位——spike 结论出来前预拆后续里程碑任务 = 写完即返工；
- todo 文档头部必须写维护约定（滚动时机、状态翻转带证据、远端迁移时机），否则写完即腐化。

## L7 · 外部依赖的"承重墙"要逐条核实并标日期

文档里的 tsgolint GA/59-61 条、JS Plugins alpha、oxc_cfg ~932 SLoC、`--type-aware` 不尊重 `--tsconfig`、TS7 不支持 `baseUrl`——全部经官方来源核实并标注日期（2026-09）。其中 TS7/baseUrl 一条直接打在设计自己的 `baseUrl` 对齐要求上（§4.2），不核实就会在 M2 才发现。
**沉淀**：写进权威文档的外部事实 = 官方域名 > GitHub changelog > 官方博客，逐条带核实日期；与自身其他条款冲突的外部约束（如 baseUrl）要当场把兜底方案写进设计。
