# SAST Review

对 SAST 引擎/静态分析项目做仓库级、多维度、可复现的独立评审。目标不是复述 README，而是回答三个问题：架构能否长期演进、检测能力处于什么水平、是否具备替代现有引擎的条件。

## 何时使用

- 用户要求评价/评审一个 SAST 引擎、静态分析项目、lint 平台或检测引擎。
- 替代现有引擎前的技术尽调、选型对比、架构评审。
- 需要评分卡、关键问题清单、整改路线图。

不适用：普通业务代码 review（用 [code-review-dimensions](../belos-street/reference/code-review-dimensions.md)）、单文件风格问题、从零写代码。通用仓库质量评估可叠加 [project-evaluator](../belos-street/reference/project-evaluator.md)；规则质量评审叠加 [rule-authoring](../rule-authoring/SKILL.md)；oxc/oxlint 细节查 [oxc-toolchain](../oxc-toolchain/SKILL.md)。

## 评审立场（先立规矩）

1. **独立**：不继承任何既有结论。已有结论时先列出，再逐条重新取证；不拿结论当证据。
2. **对抗但公允**：默认假设“宣称可能不成立”，但必须双向取证——既列优点也列缺陷。
3. **证据先行**：每个评分至少两条证据；每个 High 及以上问题必须有 file:line 或命令输出。
4. **口径分离**：注册/启用/有效；引擎单测吞吐/端到端吞吐；文档自报/实测；事实/推断/观点。
5. **可复现**：记录 commit、工作区状态、跑过/没跑过的命令；未验证写“未验证”。
6. **只读**：不修改源码、配置、文档；只输出报告。用户要求落盘时写入 `docs/reviews/<name>-review-vX.md`，不改其他文件。

## 工作流（七步）

1. **快照**：`git rev-parse HEAD`、`git status --short`、目录/构建文件/CI 配置；记录评估快照。
2. **声明盘点**：从 README/设计文档/升级计划提取可证伪声明（规则数、性能、召回、误报、测试数、CI、扩展性），建“声明 vs 事实”表。
3. **架构取证**：分层、依赖方向、解析器抽象、sidecar 协议、确定性、缓存/增量、并发/内存、fail-open、部署分发。
4. **SAST 取证**：检测深度 L0-L4、规则面、taint 正确性、sanitizer、source/sink、框架语义、type-aware、误报/召回、CWE/OWASP、证据链、SARIF/抑制。
5. **工程取证**：测试、CI、fixture/golden、版本锁定、跨平台、文档、供应链。
6. **评分**：按下方权重与锚点；同时给“MVP 视角”和“企业级替代视角”两个总分。
7. **输出**：结论先行 → 评分卡 → 声明 vs 事实 → 分维度 → 问题清单 → 路线图 → 局限。

详细检查项见 [review-checklist](reference/review-checklist.md)；报告骨架见 [report-template](reference/report-template.md)。

## 评分维度与权重

| 维度 | 权重 | 核心问题 |
| --- | --- | --- |
| SAST 检测深度与规则覆盖 | 25 | 检测层到 L4 哪一级？规则是否覆盖目标 CWE 家族？ |
| 精度/召回与评估方法 | 20 | 有逐行标注基准吗？分母与判定口径可信吗？ |
| 架构设计与可演进性 | 20 | 解析器可替换吗？增量正确吗？契约稳定吗？ |
| 工程质量/测试/CI | 15 | 门禁是脚本还是流水线？版本与供应链可控吗？ |
| 平台契约与集成 | 10 | 输出能被平台直接消费吗？置信度门禁可执行吗？ |
| 框架扩展性与解耦 | 10 | 加 Angular/Nest/React 要改几个文件？ |

锚点：9-10 企业级/同类最佳；7-8 强 MVP，有明确缺口；5-6 可试点，不可替代；<5 未就绪。
权重可按项目定位调整，但必须在报告中声明；同一次对比内保持一致。

## 硬性纪律（违反即报告不可信）

- **规则数量 ≠ 能力**：必须区分注册/启用/有效；不要用注册数给检测能力打分。
- **性能必须问口径**：引擎单测还是端到端？合成语料还是真实仓库？冷扫还是热扫？
- **召回必须问分母**：全部样本还是“可静态锚定”子集？精确行还是锚点内任意命中？
- **缓存必须问一致性**：跨文件/图规则是否按文件缓存？冷扫与热扫是否等价？
- **契约必须问消费方**：confidence/cweTags/pathEvents 是否存在？exit 能否只拦 error+high？
- **扩展必须问改动面**：新增框架要改几个文件？有没有 Profile/Processor/RulePack 接口？
- **不因缺少平台能力扣分**：任务、上传、基线、AI 研判由平台负责；只评价边界与契约。
- **双向抵消禁止**：不用“工程纪律好”抵消检测深度不足，也不用“规则多”抵消误报率高。

## 输出要求

- 中文，结论先行；正文 3000 字以内（表格不计）；完整版按模板十节输出。
- 每个问题：ID、严重度（Blocker/High/Medium/Low）、证据、影响、修复、验收标准。
- Top 3 结论给“什么证据会改变判断”。
- 最后给“如果只能做三件事”。

## 自检

- [ ] 记录了 commit 与工作区状态
- [ ] 声明 vs 事实表有实测/未验证标注
- [ ] 规则数三口径、性能两口径、召回分母都交代清楚
- [ ] 每个维度至少两条证据
- [ ] 冷/热扫一致性、契约字段、框架改动面三项已核查
- [ ] 报告同时有优点与缺陷
- [ ] 路线图有 P0/P1/P2 与验收标准
