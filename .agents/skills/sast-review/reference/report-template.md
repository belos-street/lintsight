## 3. 架构评估

- 分层与依赖方向
- 解析器抽象与铁律兑现
- 双引擎/sidecar 协议
- 确定性、指纹、契约版本
- 缓存/增量一致性
- 并发/内存/资源上限
- fail-open 与可观测性
- 部署与分发

每项写“现状 → 风险 → 结论”，不要逐文件复述。

## 4. SAST 专业性评估

- 检测深度（L0-L4）与目标差距
- 规则面：自有/内置/启用/有效
- taint 正确性：source/sink/sanitizer、kill、参数位、跨过程
- 框架语义：Vue/Angular/React/Nest/ORM
- type-aware 策略
- 精度/召回方法与证据
- CWE/OWASP、证据链、SARIF、抑制/基线

## 5. 工程与交付评估

- fixture/golden/注册表一致性

- 跨平台与文档漂移

## 9. 开放问题与信息缺口

- 需要平台团队提供的材料（例如现有引擎规则清单、样例诊断、误报口径）。

## 10. 评审方法与局限

- 跑过的命令与结果（test/lint/bench/corpus）。

- 文档自报 vs 实测的比例。
- 评审者可能存在的偏差（例如只读文档、只抽样部分规则）。

## 写作纪律

- 结论先行；不要按文件目录顺序写。
- 每个维度至少两条证据；没有证据的维度标“未验证”并降权。
- 区分事实、推断、观点；不要用“可能/也许”代替取证。
- 不要用规则数量、测试数量、LOC 单独证明能力。
- 不要只列缺陷或只列优点；必须双向。
- 不要把平台能力缺失算作引擎缺陷；只评价边界与契约。
- 不要给“总体感觉 X 分”；分数必须来自维度加权。
